# みちのーと SaaS本番化要求仕様

最終更新: 2026-08-14

対象: 放課後等デイサービス向け個別支援計画ワークベンチ

## 1. 目的

日誌、連絡帳、相談支援事業者の計画、事業所のアセスメント、モニタリング、個別支援計画を一つの支援サイクルとして管理し、根拠をたどれる下書きと正式帳票を作成できるWebサービスを提供する。

自動生成結果は必ず下書きとし、本人・家族の意向、面談、会議、専門職による確認、同意、交付を経て正式文書にする。システムが診断や支援方針を自動決定しない。

## 2. 対象ユーザー

| 利用者 | 主な業務 |
| --- | --- |
| SaaS運営管理者 | 法人開設、障害対応、契約状態管理。通常は児童情報を閲覧しない |
| 法人管理者 | 事業所、職員、所属、権限、法人設定の管理 |
| 施設管理者・児童発達支援管理責任者 | 利用児管理、計画作成、レビュー、承認、交付、モニタリング |
| 支援職員 | 担当利用児の日誌、連絡帳、支援実績、モニタリング下書きの作成 |
| 閲覧・監査担当者 | 許可された施設・利用児の履歴と正式文書の閲覧 |
| 保護者・外部相談支援員 | 将来提供。共有対象と期限を限定した閲覧・同意 |

## 3. 用語と文書の分離

共有された参考帳票のうち、週間計画表、申請者の現状、サービス等利用計画案は相談支援事業者が作成する文書である。放課後等デイサービス事業所が作成する個別支援計画とは別の文書として保存する。

```text
相談支援計画（上位方針）
  → 事業所アセスメント
    → 個別支援計画
      → 日誌・連絡帳・支援実績
        → モニタリング
          → 次期アセスメント・個別支援計画
```

確定済み文書は上書きせず、新版を作成する。各目標は前版の目標と系譜を持ち、日誌とモニタリング結果から追跡できるようにする。

## 4. 必須機能（P0）

### 4.1 法人・事業所・アカウント

- 法人をテナント、事業所をテナント配下の業務単位として管理する。
- 職員は招待制で登録し、複数事業所への所属を許可する。
- ロールは法人管理者、施設管理者、計画承認者、支援職員、閲覧者を最低限用意する。
- 退職・休職時の無効化、セッション強制失効、所属変更、招待期限切れを扱う。
- 管理者はMFAを必須とし、一般職員もMFAを有効化できる。
- 画面表示だけでなくAPIとDBで権限を検証する。

### 4.2 利用児台帳

- 基本情報、保護者、続柄、住所、連絡先、緊急連絡先を管理する。
- 障害・疾患、医療・服薬、受給者証、認定区分、有効期間、利用者負担上限額を管理する。
- 相談支援事業者、医療、教育、福祉、地域支援等の関係機関を管理する。
- 家族構成と関係機関は構造化データとして保存し、関係図生成に利用できるようにする。
- 受給者証番号等は画面と通常APIで常にマスキングする。正式帳票に全文が必要な場合だけ、帳票出力権限を確認したサーバー処理内でKMS復号し、メモリ上の生成入力以外へ平文を残さない。
- 利用児は施設へ割り当て、担当外の職員から参照できないようにする。

### 4.3 アセスメント

- 支援経過、現状と課題、生活歴・受診歴、健康、生活状況、本人の意向、家族の意向、強みを版管理する。
- 「現在の生活」の週間スケジュールを、曜日、開始・終了時刻、翌日跨ぎ、場所、活動、サービス種別で登録する。
- 公的支援とインフォーマル支援を別区分で登録する。
- 相談支援計画から引き継いだ内容と、事業所で追記した内容を画面上で区別する。

### 4.4 相談支援計画

- 利用者・家族の生活に対する意向、総合的な援助方針、長期・短期目標を管理する。
- ニーズ、支援目標、達成時期、サービスの種類・内容・量、本人の役割、評価時期、留意事項を複数行で管理する。
- 計画後の週間計画と週単位以外のサービスを管理する。
- 面接、説明、同意、交付を記録し、確定版PDFを不変スナップショットとして保存する。

### 4.5 個別支援計画

- 相談支援計画を参照し、事業所の支援方針、本人支援、家族支援、移行支援、地域支援を作成する。
- 5領域との関連、支援目標、支援内容、担当者、頻度、期限、評価方法、根拠日誌を保持する。
- 下書き、確認待ち、説明待ち、同意済み、承認済み、交付済み、実施中、改定、終了の状態を持つ。
- 作成者と承認者を分離可能にし、差戻し理由を保持する。
- 計画本文を変更した場合は旧同意を再利用せず、再説明・再同意を要求する。

### 4.6 日誌・連絡帳・支援実績

- 日誌は観察事実、行った支援、本人の反応、健康・活動、関連5領域、関連目標、記録者、実施日時を保持する。
- 連絡帳は家庭からの連絡、事業所からの返信、要望、計画への反映状況を保持する。
- 記録本文からのタグ付けや下書き生成は根拠を表示し、人が確認して保存する。
- 日誌・連絡帳を削除した場合も監査上の履歴を残す。確定文書の根拠となった記録は物理削除しない。

### 4.7 モニタリング

- 対象計画、対象期間、開催日時、場所、出席者、記録者を管理する。
- 計画中の長期・短期・支援目標を引き継ぎ、進捗、現状の課題、今後の支援方針を目標単位で記録する。
- 日誌件数だけで達成を自動判定せず、確認すべき根拠と変化を下書きとして示す。
- 次期計画へ引き継ぐ目標、見直す目標、終了する目標を明示する。

### 4.8 帳票・PDF

- 画面入力UIと正式帳票レイアウトを分離する。
- 参考帳票の方向は、週間計画表・現在の生活・利用計画案をA4横、基本情報・モニタリング記録をA4縦とする。
- 日本語フォントを埋め込み、長文折返し、禁則、改ページ、繰返し見出しに対応する。
- 下書きには透かしを入れ、正式版は対象文書版、テンプレート版、生成者、生成日時、ハッシュを保存する。
- 正式PDFは上書き不可とし、閲覧、印刷、ダウンロード、再出力、交付を監査記録する。
- 自治体・指定権者ごとの差異に備え、帳票テンプレートを版管理する。

### 4.9 監査・版管理

- 操作者、法人、事業所、対象、操作、日時、IP、User-Agent、リクエストIDを記録する。
- 個人情報の閲覧、検索、CSV/PDF出力、権限変更、ログイン失敗、承認、同意、交付を記録する。
- 変更差分は必要最小限にし、監査ログへ日誌本文等を重複保存しない。
- 承認済み文書は不変とし、訂正は新版または訂正記録として残す。

## 5. 複数端末とエラー時の挙動

- サーバーDBを正本とし、`localStorage` は未送信の一時退避以外に使用しない。
- 更新対象に版番号を持たせ、更新時に読込版と一致しない場合はHTTP 409を返す。
- 競合時は「別の職員が更新した」こと、更新者、更新時刻を表示し、再読込と差分確認を選べるようにする。
- 自動保存は「保存中・保存済み・通信待ち・失敗・競合」を画面と支援技術へ通知する。
- 作成APIは冪等キーを受け、再送や二重クリックで重複登録しない。
- 通信断時は入力を端末内へ暗号化せず長期保持しない。再接続後に利用者が送信内容を確認して同期する。
- APIエラーに個人情報や内部SQLを含めない。画面には復旧方法と問い合わせ用リクエストIDを表示する。

## 6. セキュリティ・個人情報

- TLS、DB暗号化、バックアップ暗号化、オブジェクト暗号化を必須とする。
- クライアントが送信した `tenant_id` を信用せず、認証済みセッションと所属情報からサーバーが決定する。
- 全業務テーブルでDBのRow Level Securityを有効化し、APIの絞り込み漏れに対する多層防御を行う。
- 秘密情報はAWS Secrets Manager等で管理し、リポジトリと配布物へ含めない。
- 本番データを開発環境、アクセス解析、生成AIへ送信しない。
- SaaS運営者は通常の操作で児童情報を閲覧できない。緊急代理アクセスは理由、期限、承認、操作履歴を必須とする。
- ログとメトリクスには氏名、障害・疾患、日誌、連絡帳、証書番号を含めない。

## 7. 非機能要件

| 項目 | 限定パイロット | 正式提供 |
| --- | --- | --- |
| 可用性目標 | 月間99.5% | 月間99.9% |
| RPO | 15分以内 | 5〜15分以内 |
| RTO | 4時間以内 | 2時間以内を目標 |
| 通常API応答 | p95 800ms未満 | p95 500ms未満 |
| 初期画面 | p75 LCP 2.5秒未満 | p75 LCP 2.5秒未満 |
| 対応端末 | Windows Chrome/Edge、iPad Safari | 同左＋主要スマートフォン |
| アクセシビリティ | WCAG 2.2 AA主要項目 | WCAG 2.2 AA |
| 保存期間 | 導入法人と法令・指定権者の確認後に設定 | 契約・規程で明文化 |

## 8. リリース判定

- テナントAからテナントBのデータを、ID変更、検索、帳票、添付、APIのいずれでも取得・変更できない。
- 全ロールと主要操作の許可・拒否テストが成功する。
- 二端末同時編集で後勝ち上書きが発生せず、競合が画面に表示される。
- 承認済み文書の本文を更新できず、新版作成が要求される。
- バックアップから別環境へ復元し、文書と添付の整合性を確認できる。
- 主要業務E2E、Windows/iPad、キーボード操作、PDF目視確認が完了する。
- 重大・高リスクの脆弱性が0件である。

## 9. 今回の前提

- 最初の導入は1法人・1〜2事業所の限定パイロットとするが、データ構造は初日から複数法人対応にする。
- 既存デモの架空データと下書き生成ロジックは残し、本番データ領域とは分離する。
- AI連携は初回正式版の必須要件に含めない。導入する場合も外部送信の同意、学習利用禁止、根拠表示、人による承認を別途設計する。
- 料金請求、保護者ポータル、外部相談支援員の共同編集はP1以降とする。
- 参考写真の実値は保存・転記せず、帳票項目と構造だけを仕様化する。
- 自治体様式と保存期間は、導入施設および指定権者の現行要件で最終確認する。
